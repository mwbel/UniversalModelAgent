结论：你现在第三栏的问题，不是单个渲染 bug，而是**数据流边界不清**。不要再让 Codex 在同一个模块里同时改 Markdown、调用 Mathpix、修公式、渲染、人工编辑、写回文件。应把第三栏改成一个**可回滚、可测试、按块 patch 的校对流水线**。

Mathpix 的主输出是 Mathpix Markdown，是 Markdown 的超集，面向公式、表格、化学等 STEM 内容；MinerU 本身是把 PDF / 图片等解析为 Markdown / JSON 的文档解析工具；Typora 的数学渲染依赖 MathJax。三者的 Markdown / LaTeX 方言并不完全等价，所以“Mathpix 识别正确但 Typora 渲染失败”是正常风险，不应直接把 Mathpix 输出写入最终稿。([Mathpix Docs](https://docs.mathpix.com/?utm_source=chatgpt.com))

## 1. 第三栏应重新定义为“校正工作台”，不是 Markdown 编辑器

第三栏建议拆成 6 个子层：

| 层级               | 职责                                                     | 不允许做什么      |
| ------------------ | -------------------------------------------------------- | ----------------- |
| Block Parser       | 把 MinerU Markdown 切成 block，生成 block_id             | 不修内容          |
| Risk Detector      | 判断哪些块高风险，例如公式闭合、漏行、表格、矩阵         | 不调用 API        |
| Mathpix Corrector  | 只对指定 block 或 bbox 图像调用 Mathpix                  | 不写回文件        |
| Dialect Normalizer | 把 Mathpix Markdown / LaTeX 转成你项目统一 Markdown 方言 | 不改业务逻辑      |
| Patch Merger       | 生成 block 级 patch，支持人工修改和回滚                  | 不渲染            |
| Renderer Adapter   | 渲染预览，显示错误位置                                   | 不修改源 Markdown |

核心原则：**源文件不可直接被渲染层、API 层、编辑器层修改。所有修改必须先变成 patch。**

## 2. 必须建立统一中间格式，不要直接操作 Markdown 字符串

建议建立一个内部数据结构，例如：

```ts
type OcrBlock = {
  blockId: string;
  pageNo: number;
  blockType: "paragraph" | "display_math" | "inline_math" | "table" | "figure" | "caption" | "unknown";
  source: "mineru" | "mathpix" | "human";
  rawText: string;
  normalizedText: string;
  bbox?: [number, number, number, number];
  riskFlags: string[];
  renderStatus: "ok" | "warning" | "error";
  provenance: {
    mineruHash?: string;
    mathpixJobId?: string;
    humanEditedAt?: string;
  };
};
```

最终不要直接说“替换第 35 行到第 42 行”，而是说：

```ts
type OcrPatch = {
  patchId: string;
  blockId: string;
  oldHash: string;
  newText: string;
  source: "mathpix" | "human" | "auto_normalizer";
  status: "draft" | "accepted" | "rejected";
};
```

这样可以避免 Codex 一改就牵连全局。

## 3. 针对你列出的 3 类问题，分别设边界

### 问题 1：MinerU 多加或漏加 `$$`

不要让 Codex 到处写正则修复。应做一个独立模块：

```txt

```

它只负责：

| 输入            | 输出                            |
| --------------- | ------------------------------- |
| 原始 block 文本 | 规范化后的 block 文本           |
| block 类型判断  | 是否 display_math / inline_math |
| 错误列表        | 例如 unclosed_math_delimiter    |

建议规则：

1. block 内如果已有 `\begin{equation}`、`\begin{align}`、`\begin{array}`，不要再无脑包 `$$`。
2. display math 一律规范为：

```md

...
$$
```

1. inline math 一律规范为：

```md

```

1. 禁止跨 block 自动补 `$$`，跨 block 修复必须进入人工确认队列。

### 问题 2：MinerU 漏行

这是 OCR 覆盖问题，不是 Markdown 渲染问题。不要靠渲染器修。

建议新增：

```txt
coverageChecker.ts
```

它比较：

| 来源             | 检查方式                 |
| ---------------- | ------------------------ |
| PDF 页面图像     | 行 / block bbox          |
| MinerU JSON      | block 数、bbox、文本密度 |
| Mathpix 整页结果 | 行级差异                 |
| 人工视图         | 高亮疑似漏行区域         |

漏行检测不要一开始追求完美，先做启发式：

```txt
1. 当前页 MinerU block 数明显少于 Mathpix block 数

5. Mathpix 整页有内容，但 MinerU 当前 block 附近为空
```

输出不应直接修文件，而是生成：

```ts
riskFlags: ["possible_missing_line"]
```

然后让第三栏出现“疑似漏行，建议调用 Mathpix 局部识别”。

### 问题 3：Mathpix 校正正确但渲染失败

根因通常是**方言不一致**。Mathpix Markdown 是自己的扩展 Markdown，而 Typora 使用 Markdown + MathJax 渲染路径；这两个体系并不保证完全兼容。([Mathpix Docs](https://docs.mathpix.com/?utm_source=chatgpt.com))

你需要一个：

```txt
mathpixToTargetMarkdownAdapter.ts
```

它只做一件事：把 Mathpix 输出转成你项目选定的目标格式。

建议你明确目标格式：

```txt
Target Markdown Dialect:
1. Markdown: CommonMark-compatible subset
2. Math renderer: MathJax-compatible LaTeX
3. Display math: $$ ... $$
4. Inline math: $...$
5. Tables: GitHub-style Markdown table where possible
6. Complex tables/matrices: 保留 LaTeX 环境，不强制转 Markdown 表格
```

不要直接信任 Mathpix 输出。Mathpix 输出进入项目后必须经过：

```txt
Mathpix raw output
→ syntax sanitizer
→ delimiter normalizer
→ renderer compatibility check
→ patch preview
→ human accept
→ write back
```

| 业务层 | 非 VIP 消费者生命周期、转化路径、顾问动作 |
| 数据层 | HIS/CRM/问卷/访谈/行为数据                |
| 策略层 | 细分关注点、行为经济学偏差、决策旅程      |
| 生成层 | 客户画像、任务卡、H5 内容、顾问话术       |
| 风控层 | 投诉、退款、低满意度、敏感表达拦截        |
| 工程层 | 数据库、API、权限、审核流、日志、前后端   |

这种系统不能让 Codex “理解后自己做”。你要把它压缩成：

1. 读一个局部规范
2. 改一个模块
3. 跑一个测试
4. 输出一个 diff
5. 不允许扩展范围

Codex 的官方技术说明也强调，Codex 不是单个模型直接魔法式写完项目，而是由 agent loop / harness 协调模型、工具、提示和执行环境完成任务。也就是说，工程效果高度依赖任务编排和上下文设计。([OpenAI](https://openai.com/index/unrolling-the-codex-agent-loop/?utm_source=chatgpt.com))

最重要的是 `AGENTS.md`。它是 Codex 每次开发前必须读取的规则文件。

示例：

```md
# AGENTS.md

Build an AI-driven non-VIP consumer lifecycle interaction engine.

## Hard Rules
1. Do not invent customer facts.
2. All customer-level conclusions must be traceable to source fields.
3. Risk flags override marketing recommendations.
4. Generated advisor tasks must be actionable, auditable, and editable by humans.
5. Do not change database schema unless the task explicitly asks for it.

1. Data ingestion
2. Customer truth extraction
3. Database analysis
4. Insight generation
5. Risk compliance
6. Advisor task card generation
7. H5 content generation
8. Feedback loop

## Output Requirements
Every generated recommendation must include:
1. customer_id
2. evidence_fields
3. inferred_need
4. confidence_level
5. risk_flags
6. recommended_next_action
7. human_review_required
```

## 4. 每次给 Codex 的任务必须像工单，不要像聊天

错误写法：

```text
帮我继续完善数据库分析 agent。
```

这会导致它发散。

正确写法：

```text
Task: Implement customer segmentation logic for non-VIP consumers.

Read first:
1. /docs/business/segmentation_rules.md
2. /docs/data/field_dictionary.md
3. /docs/engineering/testing_rules.md

Scope:
Only modify:
1. src/agents/database_analysis/segmentation.py
2. tests/agents/test_segmentation.py

Do not modify:
1. database schema
2. API routes
3. frontend files
4. prompt templates outside this module

Input:
A customer profile object with:
1. customer_id
2. visit_history
3. purchase_history
4. consultation_notes
5. complaint_records
6. price_sensitivity_score
7. trust_signals
8. service_interest_tags

Output:
Return:
1. segment_label
2. core_driver
3. behavioral_bias
4. journey_stage
5. confidence_score
6. evidence_fields

Acceptance criteria:
1. Customers with high price sensitivity and no complaints should be classified as price-transparency driven.
2. Customers with prior complaints must include risk flags.
3. No segment may be assigned without evidence_fields.
4. All tests must pass.
5. Do not invent missing fields.
```

这类任务，Codex 才容易做对。

## 5. 你应该把“复杂问题”拆成三层

### 第一层：人负责判断

这些不应该交给 Codex 自由决定：

| 事项                  | 原因             |
| --------------------- | ---------------- |
| 非 VIP 消费者分类标准 | 涉及商业判断     |
| 行为经济学解释        | 容易胡编心理原因 |
| 风险拦截规则          | 涉及合规和客诉   |
| 数据字段真值优先级    | 影响结论可靠性   |
| 顾问任务是否合适      | 影响真实客户关系 |

### 第二层：GPT 负责设计

适合让 GPT 先产出文档：

| 文档                     | 作用             |
| ------------------------ | ---------------- |
| segmentation_rules.md    | 客户细分规则     |
| behavioral_bias_rules.md | 行为偏差识别标准 |
| journey_stage_rules.md   | 决策旅程阶段     |
| task_card_schema.md      | 顾问任务卡格式   |
| risk_policy.md           | 风险和合规边界   |

### 第三层：Codex 负责执行

适合让 Codex 做：

| 开发任务               | 适配度         |
| ---------------------- | -------------- |
| 根据 schema 写数据模型 | 高             |
| 根据规则实现分类函数   | 高             |
| 写单元测试             | 高             |
| 补 API endpoint        | 高             |
| 修 bug                 | 高             |
| 大规模重构             | 中，需要强约束 |
| 自主设计完整系统       | 低             |

## 6. 对你当前项目，推荐开发顺序

不要先做复杂 Agent 群。先做一个最小可验证闭环。

### 第一步：数据真值层

目标：20 个客户数据先变成标准结构。

输出：

```json
{
  "customer_id": "C001",
  "is_vip": false,
  "known_facts": {},
  "missing_fields": [],
  "risk_events": [],
  "source_trace": []
}
```

### 第二步：画像分析层

输出：

```json
{
  "customer_id": "C001",
  "core_driver": "price_transparency",
  "behavioral_bias": "loss_aversion",
  "journey_stage": "consideration",
  "confidence": 0.72,
  "evidence": []
}
```

### 第三步：任务卡层

输出：

```json
{
  "customer_id": "C001",
  "advisor_task": "解释价格组成并提供低风险体验方案",
  "reason": "客户表现出价格敏感和尝试风险顾虑",
  "do_not_say": [],
  "human_review_required": true
}
```

### 第四步：H5 内容层

输出三屏：

```text
Screen 1: 你的当前状态
Screen 2: 你可能关心的问题
Screen 3: 一个低风险下一步
```

### 第五步：反馈学习层

记录：

```json
{
  "opened": true,
  "clicked": false,
  "booked": false,
  "advisor_feedback": "",
  "next_strategy": ""
}
```

先把这条链路跑通，再扩展 Agent。

## 7. 你需要建立“上下文包”，而不是每次重新解释项目

给 Codex 一个固定上下文文件：

```md
# CONTEXT_PACK.md

## Project
AI-driven non-VIP consumer lifecycle interaction engine.

## Users
Non-VIP consumers with incomplete conversion, low engagement, or uncertain intent.

## Business Goal
Increase trust, reduce decision friction, and generate advisor-executable next actions.

## Non-goals
1. Do not hard-sell.
2. Do not fabricate customer motivation.
3. Do not make medical or treatment guarantees.
4. Do not bypass human advisor review.

## Core Logic
Each customer must be analyzed across:
1. Core concern
2. Behavioral bias
3. Journey stage
4. Risk status
5. Recommended advisor action

## Evidence Rule
Every conclusion must link back to one or more source fields.
```

之后每个 Codex 任务开头都写：

```text
Before coding, read:
1. AGENTS.md
2. CONTEXT_PACK.md
3. relevant docs under /docs
```

## 8. 判断 Codex 是否真的失效，用这 5 个标准

| 标准                      | 如果不满足，通常不是模型问题 |
| ------------------------- | ---------------------------- |
| 有没有明确输入输出 schema | 没有就会乱写                 |
| 有没有验收测试            | 没有就无法收敛               |
| 有没有禁止修改范围        | 没有就会乱改                 |
| 有没有业务规则文档        | 没有就会胡编                 |
| 有没有真实样例            | 没有就只能写抽象 demo        |

如果这五项没有建立，换更强模型也只会部分改善，不会根治。

## 9. 我的建议

你现在应该暂停“让 Codex 继续自由开发”，先做三件事：

1. **冻结项目结构**
   明确哪些模块存在，哪些模块暂不开发。
2. **把业务规则文档化**
   尤其是非 VIP 客户分类、行为偏差、旅程阶段、风险拦截。
3. **让 Codex 只做小闭环任务**
   每个任务控制在 1 到 3 个文件，必须有测试和验收标准。

最关键的一句话：**GPT-5.5 可以参与复杂系统开发，但不能替你承担系统工程管理。你要把“聪明”从模型转移到项目结构、任务拆解、规则文档和测试体系里。**
